# 架构决策

## ADR-008：改为云端网站和白板采集端（当前优先）

状态：采用。用户异地维护，已确认服务器待本机调试完成后租赁，录像保存在云端。该决策覆盖 ADR-001 的同机部署、ADR-004 的局域网证书信任以及 ADR-005 的本机录像存储位置；单路采集、静音 MP4 与浏览器观看仍采用。

采用 React/TypeScript + Node/Express + SQLite/FFmpeg，Windows Electron 只负责采集与播放，云端 Docker Compose + Caddy + coturn。教师安装后只输入绑定码，正式安装包预设网站地址。绑定令牌可撤销、云端保存摘要、Windows DPAPI 保存密文；服务器和域名由维护者配置。

代价：依赖白板上网与云端稳定性，连续录像消耗带宽和云盘，断网不提供离线补传；TURN 公网和校园出口需实测。网站可集中更新，已加载的采集脚本需重开采集端，桌面壳仍需覆盖安装。先以本机 HTTPS 模拟验证再采购上线，不能把合成测试当作鸿合/公网验收。

## ADR-001：同机部署，局域网访问

状态：采用。原因：用户确认单间教室、单人使用、都在学校局域网。服务、采集和录像放白板，办公电脑不用常开，无云服务器费用。代价：白板必须运行，校园网需要互通。

## ADR-002：有条件选择 Windows Electron

状态：采用，待设备核实。原因：Windows 桌面壳可管理开机启动、托盘、摄像头与后台生命周期。品牌和照片不能证明摄像头向 Windows 开放；若摄像头仅由 Android 使用，需调整采集端，不能宣称现有包可直接支持。

## ADR-003：独立实现，参考既有交互

状态：采用。附件只有部分后端/桌面源码，网页缺原始源码，且包含无关课堂管理业务和现成敏感数据。采用明确需求独立实现，不运行附件程序，不复制其私钥/数据库，不依赖不完整的编译产物。

## ADR-004：浏览器统一观看

状态：采用。手机和电脑共用响应式页面，降低首版成本。手机录音需可信 HTTPS，因此每台白板生成独立 CA，观看设备首次安装信任。没有绕过系统浏览器安全限制。

## ADR-005：单流采集，录像分块落盘再生成 MP4

状态：采用。WebRTC 与 MediaRecorder 共享同一视频流，避免摄像头争用。原始 WebM 分块写本机，再以单任务 FFmpeg 生成兼容手机的 H.264 MP4。代价：需要额外编码开销，录像结束后才能回放，切段和真机性能需验收。

## ADR-006：文档与可执行检查作为交付约束

状态：采用。通过 AGENTS 索引、需求基线、决策记录、测试、进度证据和真机验收清单形成 Harness 闭环。测试失败先定位，不把未运行的检查列为通过；每轮交付更新进度。

## ADR-007：Windows 视频采集兼容配置

状态：采用，待鸿合真机复核。当前 Windows 环境下，Electron 合成摄像头启动后独立采集服务崩溃，日志为 `Detected crash of video capture service`，随后媒体轨结束和设备消失。初次尝试关闭旧 `VideoCaptureService` 特性后偶尔通过，完整复测仍失败，因此未将该尝试作为最终方案。

最终启用 Chromium `RunVideoCaptureServiceInBrowserProcess`，使视频采集服务在浏览器主进程中运行。同样的完整浏览器和 Electron 媒体测试通过，包含直播、录像和喊话。Windows 主进程启动前设置此兼容开关，浏览器测试使用相同配置。保持渲染窗口 sandbox、上下文隔离和受限媒体授权；不全局禁用沙箱。该配置验证了本机合成媒体路径，不证明任何特定鸿合驱动已兼容。
